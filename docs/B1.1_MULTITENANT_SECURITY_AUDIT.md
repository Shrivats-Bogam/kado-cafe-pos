## 1. Tenant Architecture & Boundary Hierarchy

```text
Supabase Auth User
        ↓
Organization Membership (`organization_members`)
        ↓
Organization (`organizations`)
        ↓
Role (`Owner`, `Manager`, `Cashier`, `Staff`, `Kitchen`)
        ↓
Tenant Data (`organization_id = auth.current_organization_id()`)
```

- **Authoritative Tenant Boundary**: `organization_id` is enforced by PostgreSQL Row Level Security (RLS) policies. Client tampering with `organization_id`, `role`, or `user.id` in `localStorage` or REST request payloads is rejected by the database.

## 2. Organization Provisioning & Invitation System

Created [`supabase/b11_multitenant_saas.sql`](file:///C:/Users/Admin/.gemini/antigravity/worktrees/kado-cafe/redesign_tables_pos_ui/supabase/b11_multitenant_saas.sql):
- **`pos_organization_invitations` Table**: Tracks invitation IDs, organization IDs, emails, roles, 64-character hex tokens (`invitation_token`), statuses (`pending`, `accepted`, `expired`, `revoked`), and 7-day expiration timestamps.
- **RPC `provision_organization_transaction`**: Atomically provisions organization, seeds default settings and categories, and assigns owner membership.
- **RPC `create_organization_invitation`**: Generates cryptographically secure 64-character token and inserts invitation (restricted to Owner/Manager).
- **RPC `accept_organization_invitation`**: Validates active non-expired token, creates `organization_members` record, and marks status `accepted`.
- **RPC `switch_organization_context`**: Validates user active membership in target organization before allowing context switch.
